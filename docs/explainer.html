How Chat is built

Chat is a small open model running on a shared 4-core server with no GPU, behind one thin, guarded API. The model is the last thing a question reaches: limits, a topic screen and a site fact sheet come first, and the reply is screened again on the way out.

The system

One public piece, the model out of reach

Ollama's API has no authentication and no limits, so it has no route from outside the Docker network. chat-api is the only thing the internet can reach; Radar's Ask uses the same Ollama from inside the network. n8n and Flowise are bound to localhost, reachable only through an SSH tunnel, and configured but not running.

  • Traefik TLS for chat.naveenlabs.tech only
  • chat-api FastAPI: limits, screens, fact sheet
  • Ollama gemma3:4b, pinned image, internal only
  • radar-web Radar's Ask, same model server
  • n8n, Flowise localhost only; can run shell commands, so never public
  • Uptime probe calls /healthz from outside, like a visitor

The rule behind every design choice

The model is the last line, not the first

A small local model will answer anything it is sent, as often as it is sent. So every question meets cheap checks in code first, and the model only runs when they pass. The order matters: the cheapest, most certain checks run first.

chat-api/main.py, the whole route (shortened)
def chat(req, request): ip = _client_ip(request) # rightmost X-Forwarded-For if _rate_limited(ip): raise HTTPException(429) if _over_daily_cap(ip): raise HTTPException(429) if _SELF_HARM.search(req.message): return {"reply": SUPPORT} if _BLOCKED.search(req.message): return {"reply": REFUSAL} if not _slots.acquire(blocking=False): raise HTTPException(503, headers={"Retry-After": "5"}) ... # Ollama, 180 s timeout return {"reply": REFUSAL if _BLOCKED.search(reply) else reply}

Why a separate service

Exposing Ollama would hand anyone an unauthenticated, unlimited model server on a shared box. chat-api is about 200 lines of Python and holds every limit and guardrail.

Why this order

Rate and daily limits cost nothing and protect the box. The screens are regular expressions in the same process, no model. The concurrency slot is taken last, so a refused question never holds one.

ResultA blocked question is refused in 0.1 s on the live site, and the model never sees it.

Guardrails, and what they are not

Two cheap layers, stated honestly

1 · Topic screen, both ways

A keyword list for weapons, malware, phishing and scams, drugs and sexual content. It checks the question before the model and the reply after it; a matching reply is replaced with the refusal.

2 · System prompt

Refuses harmful, illegal and sexual requests and scams; gives no medical, legal or financial advice; never claims to be made by, or speak for, any company; says so when unsure.

Self-harm gets help, not a refusal

A separate pattern answers with a supportive message and India's Tele-MANAS helpline, 14416 (free, 24x7), before anything else runs.

chat-api/main.py
# ponytail: keyword screen, not a classifier; a small local model # can't run a safety model alongside it. _BLOCKED = re.compile(r"""(?ix) \bphishing\b | \bransomware\b | ...""")
What it is notA keyword list misses paraphrases; the system prompt is the second layer, and the reply screen the third. On a 4-core box with no GPU, a second safety model would double every reply's time.
Grounding without a vector store

A small model invents, so it gets checked briefs

Asked about this site, a small model made up answers about its own projects. The fix is one checked brief per project (intro, architecture, strengths, intelligence). A project question gets the model with that project's whole brief, strict rules and temperature 0; code then checks every number in the answer against the brief and falls back to the checked section if one is not there.

chat-api/briefs/trust.md (shortened)
## Intro Trust is a security checker for MCP servers ... <!-- more --> (the detailed form, for "More on ...") ## Architecture ... ## Strengths ... ## Intelligence ... Routing (chat-api/briefs.py): - "How is Trust built?" -> model + whole Trust brief - "how is it tested?" -> same, last project shown - "Can I trust you?" -> model, general (everyday word) - answer has a number the brief lacks -> checked section instead - anything else -> model, general

Tests keep the facts honest

  • Every brief has the four sections in a short and a detailed form.
  • A project question gets that project's whole brief, at temperature 0.
  • An answer with a number the brief does not hold is replaced by the checked section.
  • No brief or prompt names a broker, an exchange, a server address or a private tool.
Trade-offThe briefs are kept in step by hand when a project changes. Reading the whole brief costs about 15 to 20 seconds before the first word; the owner chose correct over fast.

One shared box

The model may never take the last core

A reply once used all 4 cores and left the other apps on the server waiting. Now Ollama is capped at 3 CPUs and runs exactly 3 threads, so it can never take the fourth core; chat-api is capped at half a CPU. Memory is capped too.

  • Ollama cpus 3.0, num_thread 3: more threads than cores only gets throttled
  • chat-api 0.5 CPU, 256 MB
  • Memory Ollama 6 GB: at 4 GB, two loaded models were killed
  • 2 at once a third question gets 503 and a retry in 5 s

A bug worth telling

Every visitor saw "Model unavailable"

1
Symptom
After an Ollama restart, every question failed with "Model unavailable, try again shortly", and kept failing.
2
Cause
Loading the model from disk on a CPU takes 50-60+ s. chat-api waited 60 s then, gave up, and a timed-out request aborts the load. So the next question started the load again, and lost again.
3
Fix
OLLAMA_KEEP_ALIVE=-1: the model is never unloaded. And a warm-up step in the deploy notes: after any Ollama restart, load the model once by hand before visitors arrive.
4
Lesson
A timeout that is shorter than a cold start turns a slow first request into a permanent outage. Keep the model warm, or make the first load independent of a visitor's request.

In memory, on purpose

The limiter and the daily counters live in the process. One container on a personal site: a restart resetting them is acceptable, and there is no Redis to run or secure.

Why the rightmost address

Behind Traefik the socket peer is the proxy. The leftmost X-Forwarded-For entry is whatever the client claims; the rightmost is the one the proxy saw.

CeilingIf Chat ever runs as more than one container, the limits must move to a shared store; the code says so in a comment where it matters.

Testing and operations

Small, and tested like it matters

32 tests

  • 17 for the API: limits, daily caps, the slot freed when the model fails, refusals without the model, the reply screen, headers, health check, fact sheet rules.
  • 15 for the page: both themes define every colour, WCAG AA contrast, size budgets, no inline code, replies rendered as text only.

Hardened container

  • Non-root user, read-only filesystem, all capabilities dropped, no-new-privileges.
  • Strict CSP, HSTS, frame-ancestors 'none'; API docs turned off.
  • Pinned Python dependencies and Ollama image.

Deploy

  • Copy the files, docker compose up -d --build ollama chat-api, wait for healthy.
  • The health check polls every 2 s while starting, so the proxy routes within seconds.
  • After any Ollama restart: load the model once.

Nothing is stored

No database and no accounts: chat-api keeps only per-address counters in memory, and the question and reply live in the visitor's page. The code does not log what was asked.

Still openn8n and Flowise use :latest images. Harmless while they are off; pin them before either is started.
